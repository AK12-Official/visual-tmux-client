## 4. 剩余发现

### I18N-R2-01：目录加载及导航失败仍显示英文持久错误

**级别：P2。状态：未修复。证据：静态审阅及 DOM 探针复现。**

代码位置：

- [FileManagerOverlay.vue:589](../hub/web/src/components/files/FileManagerOverlay.vue#L589)，`startDirectory()` 初始目录加载失败。
- [FileManagerOverlay.vue:522](../hub/web/src/components/files/FileManagerOverlay.vue#L522)，`goTo()` 写入 `failure`。
- [FileManagerOverlay.vue:524](../hub/web/src/components/files/FileManagerOverlay.vue#L524)，`goTo()` 写入 `navError`。

**触发条件与复现步骤：**

1. 将界面语言设为简体中文。
2. 打开文件管理器，工作目录为 `/srv/work`。
3. 让目录列表请求返回 HTTP 403，响应体为 `{"error":"permission_denied"}`。
4. 查看文件管理器的持久错误区域。

本轮使用 `@vue/test-utils` 挂载真实文件管理组件、替换 fetch 响应进行复现，输出为：

```text
Chinese file manager failure: /srv/work could not be opened (permission_denied).
```

**根因：** `startDirectory()` 已调用本地化的 `report()`，但同时将英文模板写入 `failure.value`。通知消失后，英文错误仍留在面板中。`goTo()` 的失败分支也直接拼接英文；这些状态保存的是最终字符串，没有足够结构在切换语言后重新翻译。

**影响：** 中文模式下，文件管理最关键的失败恢复页面仍为英文和裸错误码；切换语言不会更新已有错误。此问题不改变文件权限判断，但不满足持久错误随当前语言展示的规格要求。

**修复建议：**

- 使用结构化错误状态保存展示键、路径、原始错误码或诊断。
- 在计算属性或模板边界通过 `t()` 和错误原因映射生成整句文案。
- 已知错误提供可理解的原因，未知错误保留原始诊断。
- 初始目录失败、导航失败与通知共用一致的消息规则，避免仅翻译临时通知。

**验收建议：**

- 覆盖初始目录读取失败与已有目录中的导航失败。
- 英文/中文下分别检查权限拒绝、主机不可达和未知错误。
- 错误可见时双向切换语言，确认文本更新、路径不变、错误恢复行为不变。

### I18N-R2-02：主机提交失败仍直接展示已知错误码

**级别：P2。状态：未修复。证据：静态审阅及 DOM 探针复现。**

代码位置：[HostManagerModal.vue:463](../hub/web/src/components/HostManagerModal.vue#L463)，`onSubmit()` 的异常处理；`displayGeneralError` 对 `raw` 分支直接返回原文。

**触发条件与复现步骤：**

1. 将界面语言设为简体中文。
2. 打开主机管理，新增主机并选择“本机执行”。
3. 填写合法 ID 和名称并提交。
4. 让 POST 接口返回 HTTP 409，响应体为 `{"error":"duplicate_local_host"}`。
5. 查看表单顶部错误区域。

本轮 DOM 探针输出为：

```text
Chinese host submit failure: duplicate_local_host
```

该错误码是服务端已有的明确业务错误，并非人为构造的未知诊断。

**根因：** 修复将通用表单错误改成支持 key/raw 的联合类型，但 `onSubmit()` 的所有异常依然直接进入 `{ raw: ... }`。因此通用错误尚未接入已知错误映射。探测错误已有单独映射，提交错误没有使用同等处理。

**影响：** 用户无法从中文表单理解重复本地主机、版本冲突等已知失败原因。保留机器错误码有助排查，但不能替代本地化说明；未知错误也应有本地化上下文。

**修复建议：**

- 为主机新增/更新错误建立稳定代码到展示键/参数的映射。
- 至少覆盖 `duplicate_local_host`、`host_revision_conflict`、`host_not_found` 等实际接口会返回的错误。
- 未知异常使用本地化失败说明，并保留原始诊断。
- 在展示边界翻译，保持 API 错误与业务分支使用的机器标识不变。

**验收建议：**

- 在两种语言下测试新增重复本地主机、编辑版本冲突和未知异常。
- 在通用表单错误可见时切换语言，不重新提交也应更新说明。
- 验证错误后的表单数据保留，冲突处理、重试及提交防重行为不变。

### I18N-R2-03：通知与部分界面标签仍有提取遗漏及重复前缀

**级别：P3。状态：未修复。证据：静态审阅。**

代表性位置：

| 位置 | 遗留问题 |
| --- | --- |
| [ToastStack.vue:17](../hub/web/src/components/ToastStack.vue#L17) | 通知区域 `aria-label="Notifications"` 未翻译 |
| [ToastStack.vue:28](../hub/web/src/components/ToastStack.vue#L28) | 关闭按钮 `aria-label="Dismiss notification"` 未翻译；级别标签也仍为 ERROR/WARN/INFO |
| [HostManagerModal.vue:644](../hub/web/src/components/HostManagerModal.vue#L644) | 固定英文 `Atomic Overwrite:` 与包含中文前缀的词条拼接 |
| [App.vue:322](../hub/web/src/App.vue#L322) | 浏览器拒绝全屏的警告仍为英文 |
| [App.vue:393](../hub/web/src/App.vue#L393) | 跨主机路径插入警告仍为英文 |
| [App.vue:400](../hub/web/src/App.vue#L400) | 没有可用终端时的警告仍为英文 |
| [TerminalView.vue:78](../hub/web/src/components/TerminalView.vue#L78) | 终端初始化失败的说明前缀仍为英文 |

**可观察结果：** 主机能力支持原子覆盖时，中文词条是“原子覆盖: 支持”，代码仅尝试移除英文前缀，因此最终可拼出 `Atomic Overwrite: 原子覆盖: 支持`。通知关闭按钮等辅助文本也不随语言切换。

**影响：** 不影响底层操作，但会造成中英混用、重复标签，以及辅助技术读出的语言与页面语言不一致。

**修复建议：**

- 提取应用自行生成的可见文案、title、placeholder 和 aria-label。
- 原子覆盖能力直接渲染完整词条，不对译文进行英文字符串替换。
- 不翻译主机名、路径、终端输出和原始外部诊断；仅翻译应用提供的说明。

**验收建议：** 两种语言下触发上述通知并检查可访问名称；检查主机能力标签没有重复前缀。词条一致性测试之外，应增加实际使用路径的断言，因为两份词条结构一致不代表界面已经全部使用词条。

## 6. 代码质量评价

本轮修复保持了机器标识与展示文案的分离方向；表单字段错误和认证错误从最终字符串改为结构化状态，解决了已显示错误的语言切换问题。大量文件操作提示采用整句插值，也比拼接翻译片段更便于维护。

不足在于同类路径处理方式尚未统一：字段错误保存 key，通用提交错误保存 raw，文件导航又保存英文成句文本。这使后续补语言或调整错误解释时仍需逐处排查。建议用小型、明确的展示错误结构与各业务域的代码映射收口，避免再增加根据已翻译文本反推错误类型的逻辑。

现有共享词条及参数一致性测试有价值，但只能检查翻译资源本身。对于完整覆盖，应将成功/失败/恢复状态、通知和无障碍标签纳入实际组件回归。
