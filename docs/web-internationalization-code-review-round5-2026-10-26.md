## 4. I18N-R5-01：认证内存降级无法覆盖旧存储令牌或显式退出状态

**级别：P2。状态：未修复。证据：主 Agent 与三位独立审查者的运行时探针及代码审阅。**

位置：

- [api.ts:35](../hub/web/src/api.ts#L35)：`getToken()` 优先返回任何非 null 的存储内容。
- [api.ts:41](../hub/web/src/api.ts#L41)：`setToken()` 写入失败后设置 memoryToken，但该值可能被旧存储内容遮蔽。
- [api.ts:50](../hub/web/src/api.ts#L50)：`clearToken()` 清空 memoryToken 并尝试删除存储；删除失败后没有当前页面的显式无令牌状态。
- [storageUnavailable.dom.test.ts:172](../hub/web/src/storageUnavailable.dom.test.ts#L172)：写入失败用例的 getItem 总是返回 null，未覆盖旧值仍可读的情况。

### 触发条件

Web Storage 并非所有故障都表现为读写全部禁止。例如已有值仍可读取，但写入因配额失败；或所在环境允许读取，写入/删除受限。

当前实现正确处理了 getter 抛错或读取抛错的降级，但处理不了“读取成功且旧值存在，写入或删除失败”的状态。

### 复现 A：输入新令牌后请求仍发送旧令牌

1. 让存储包含 `visual-tmux-client-token = old-token`。
2. getItem 正常读取旧值，setItem 抛 QuotaExceededError。
3. 调用 `setToken('new-token')`。
4. 调用 getToken，并通过 authFetch 捕获请求 Authorization 头。

主 Agent 实际输出：

```text
after setToken new: old-token
authorization: Bearer old-token
```

**影响：** 新令牌虽保存到 memoryToken，但实际请求继续使用旧凭据。旧令牌失效时，用户重新输入正确令牌仍无法恢复认证。

### 复现 B：退出后旧令牌重新从存储中出现

1. getItem 仍能读取旧令牌。
2. removeItem 抛异常。
3. 调用 clearToken，再调用 getToken。

主 Agent 输出：

```text
after clearToken: old-token
```

**影响：** 当前页后续 API 请求仍可能发送原令牌，与明确退出或认证失败清理的意图不符。该发现不意味着服务端会接受已经失效的凭据，也不意味着发生了认证绕过。

### 根因与归因

当前 memoryToken 的 null 同时表示“没有内存覆盖值”和“已经明确退出”，getToken 又固定优先存储，因此无法维护当前页 set/clear 操作的权威状态。

旧实现也可能在写入/删除失败后继续读取旧令牌，所以不能将所有表现描述为全新的安全回归。本轮问题是 **第四轮存储降级修复不完整，以及新增 memory fallback 的状态优先级不正确**；新增降级测试只覆盖无旧值或不可读场景，漏掉了这个组合。

### 修复建议

- 明确区分“尚未初始化的令牌状态”“当前页已经设置的令牌”和“当前页明确清除的令牌”。
- setToken 后，即使持久化失败，本页请求也必须使用用户最新提交的令牌。
- clearToken 后，即使删除失败，本页 getToken 必须返回 null，后续请求不得再从旧存储恢复令牌。
- 保持正常持久化、认证失败清理和退出行为；如调整读取策略，需要明确跨标签页更新语义，避免无意改变既有行为。

### 验收标准

1. 预置旧令牌，setItem 抛错：getToken 和 authFetch 均使用新令牌。
2. 预置旧令牌，removeItem 抛错：clearToken 后 getToken 为 null，authFetch 不携带旧令牌。
3. getter/getItem 抛错：应用仍能启动，语言切换、内存认证和退出可用。
4. 存储正常时：令牌可持久化，正常刷新及清除行为不退化。
5. 针对可读但不可写/删的环境增加实际请求头断言，不能只检查 memoryToken 或 helper 返回值。

新增存储测试比上一轮 helper 测试更接近真实使用：确实挂载 App，并检查内存令牌可用于认证请求。但 quota 用例让 getItem 永远返回 null，不能证明存在旧令牌时也正确。

终端复制提示测试中存在直接调用 translator 再调用 hook 的断言，它证明词条内容而非完整键盘事件路径；本轮代码检查确认实际分支已调用对应词条，因此仅列测试边界，不额外作为产品缺陷。
